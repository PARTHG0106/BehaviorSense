
At 20 Hz that's **45 seconds of video**, and it *refuses* rather than truncates — deliberately, per its own comment: "a report over the first 20 seconds of a ten-minute video, presented as a report over the video, is the kind of quiet misrepresentation this project keeps finding and removing." Your clip was 601 frames, so 30 s, comfortably under.

A 45-second 640×480 clip is a few megabytes. To reach 60 MB inside 900 frames you'd need something like 4K or near-lossless, where decode time would break first. So in every realistic case the size cap is inert.

What the size check *is* genuinely for — and this part I'd defend:

- It runs **before the streaming response begins**, while an HTTP status is still available. Once headers are sent for the NDJSON stream, 413 and 422 stop being options ([_generate.py:3673](notebooks/_generate.py:3673)).
- It's checked incrementally against 1 MiB chunks written straight to disk, so a huge body can't exhaust Kaggle's RAM before the check fires. That's also why the RAM ceiling isn't a function of this number.

So it's a coarse guard against someone posting a 2 GB file, not a considered capacity figure. 60 was a guess.

The real wart is the ordering. Size is checked as bytes arrive; frames are counted only after decode starts. So a 55 MB three-minute 1080p clip passes the size check, gets fully transferred and written to disk, and *then* gets rejected for frame count. And nothing tells you either limit up front — `/health` returns `max_upload_mb` but no part of the page renders it, and the file picker is a bare `accept="video/*"`.
