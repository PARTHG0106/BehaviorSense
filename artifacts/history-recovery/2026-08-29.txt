## 2. Agent 2: ensemble the streams

You're serving `bone` only at τ=0.25. If notebook 04 evaluated joint/bone/motion separately, a **logit-level ensemble** (even a simple average of joint+bone) is usually worth 1–3 points on ST-GCN++-style models at near-zero serving cost — the streams' errors are decorrelated. If 04 selected `bone` because it won alone, re-check whether it beats the *fusion*, not just the other single streams.

Also worth testing: **overlapping windows with vote/logit averaging** instead of disjoint 1.5 s windows — cheap temporal TTA that smooths boundary flicker before Viterbi even runs.

## 3. Agent 2: learn the Viterbi transition matrix

If the transition matrix in `calibrate → fusion → Viterbi → abstain` is hand-set, estimate it from the training corpora's segment sequences (Toyota Smarthome has real ADL transitions). Hand-tuned self-transition probabilities are the usual source of either over-smoothing (missed short actions like drinking) or flicker.

## 4. Agent 1: keypoint smoothing and track hygiene

- A **OneEuro or Savitzky–Golay filter** over keypoints before windowing reduces the jitter ST-GCN++ has to be robust to — this is a standard free accuracy bump for skeleton action recognition.
- Your 3 unusable pose records out of 601 are fine, but check *where* they fall: if they cluster at track handoffs, short-gap **track re-linking** (bridge gaps ≤ N frames by IoU/velocity) prevents one person becoming two tracks, which would split segments and corrupt per-subject features.

## 5. Agent 3: normalize by observation window

Several features are duration-shaped (`walking_duration_s`, `sitting_duration_s`). Comparing raw durations from a partial day against full-day reference medians is only meaningful with the reliability gate. A more accurate framing for short observations is **rate-based features** (fraction of observed time walking) compared against rate-based baselines — then a 29 s cooking clip reads "cooking fraction 1.0" rather than "walking −100%".
