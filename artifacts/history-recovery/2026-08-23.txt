Fair challenge — especially given your standing "use everything" directive. The honest answer is one principle plus three legitimate uses I'm *not* using yet, ranked.

## The principle: serving parity

The deployment input is fixed: **arbitrary user-uploaded RGB → RTMO → 17-joint COCO 2D**. A phone video or CCTV feed has no Kinect. So anything that must exist at *serving* time can only be built from RGB. That kills depth and 3D skeletons as **direct model inputs** — not because they're low-quality (V1.2 is the opposite), but because a model that consumes them is a model you can never run for a user.

This isn't hypothetical caution. This project has already paid twice for train/serve skew: `normalise()` erased falls (AUROC 0.466), and the fall head's val AUROC 1.000 sat next to held-out 0.47 because in-domain negatives were separable by nuisance cues. Adding a third instance of that class of bug is the risk.

But "can't be an input" ≠ "can't help." Here's what each mount is actually for:

| mount | as direct input | legitimate train-time use |
|---|---|---|
| `toyota-smarthome-skeleton-v1-2` (16,115) | ✗ 15-joint 3D LCR-Net, serving is 17-joint 2D RTMO | **QA reference** + **extra occlusion-robust training windows** |
| `toyota-smarthome-skeleton` (V1.1) | ✗ | nothing — **superseded by V1.2** (SSTA-PRS refined it for exactly occlusion/truncation). Using both invites citing the wrong version |
| `pose-untrimmed` (536) | ✗ | same as V1.2, untrimmed half — only relevant if the untrimmed extraction proves its worth |
| `toyota-smarthome-depth` (both) | ✗ no depth at serving | **distillation teacher only** (train with depth, infer without) |
| `msmt17` | ✗ | already used — the ReID operating point τ=0.355 is *fitted on it* |

## The three real uses, ranked by gain-per-day

**1. V1.2 as a QA reference for the extraction — cheap, do it first (~2–3 h).**
SSTA-PRS refined these skeletons specifically to fix occlusion and truncation — which is precisely RTMO's weakness. Sampling ~100 clips and comparing RTMO's per-joint visibility against V1.2's gives you a *measured* answer to "how often does our pose estimator fail, and on which activities" — the exact failure mode that produces confident nonsense windows. That number also belongs in the dissertation as a perception-quality result.

**2. V1.2 converted to COCO-17 windows as extra training data — real lever, decide after the first Toyota numbers (~1 day).**
The conversion is mechanical: project 3D→2D (orthographic + bbox scaling; our `normalise()` makes windows scale/translation invariant, so pixel-exactness matters less than it seems), map 15→17 joints, set the 5 missing face joints to confidence 0. That yields occlusion-robust windows for exactly the classes that are starving — `personal_hygiene` at 9,360 frames and `taking_medication` at 0.56% are the ones where extra windows could actually move F1. The risk is estimator-domain gap (LCR-Net 2D ≠ RTMO 2D distribution), which is why I'd **measure first**: if the plain RTMO-trained 31-class head lands near the published ceiling already, the marginal gain is small and this stays cut; if the tail classes are starving, this is the cheapest fix available.

**3. Depth via privileged distillation — the big one, and the one to cut (~2 days + retraining).**
Train a teacher on depth+3D (where occlusion doesn't exist), distill its logits into the RTMO student. Literature gain is 1–3 points and it's the only way depth contributes at serving. But it's a second model family, a distillation harness, and a retraining cycle — with one month left, Toyota base training and RT-DETR wiring both outrank it.

**Modality decisions** (answering "why not the other datasets") — serving parity is the principle: deployment is RGB → RTMO → 17-joint COCO 2D, so depth and 15-joint 3D skeletons can't be direct inputs. Three legitimate train-time roles ranked: V1.2 as QA reference (~2–3 h, do first); V1.2→COCO-17 as extra occlusion-robust windows (~1 day, gated on whether the first Toyota training shows starving tail classes); depth via privileged distillation (~2 days, cut for now). **Qwen3.5-9B analysis** — exists (Feb 2026, Apache-2.0, hybrid Gated DeltaNet, 262K context, natively multimodal), but: 18 GB weights don't fit one 16 GB serving card; DeltaNet needs `causal_conv1d`/`fla` or it "silently falls back to slower and more memory-hungry" paths; needs `transformers>=5.2` under `outlines>=1.0`; multimodality weakens the pixel-boundary claim from structural to procedural; and the gain is on the wrong axis (verifier catches unfaithful claims regardless).
