The cause is arithmetic: at 20 fps source and `FPS_SAMPLE = 12.5`, the integer stride is `round(20/12.5) = 2` → effective **10 Hz** → a 30-frame window spans **3.0 s** → any clip shorter than 3 s yields *no window at all*. ## Fixed

- **`FPS_SAMPLE = 20.0`** → stride 1, window **1.50 s**, minimum clip 1.5 s. Estimated **~322k windows** vs 97,787. And 1.50 s is *closer* to the Charades shards' 2.0 s than 3.00 s was, so window-extent consistency improves at the same time.
- **Adaptive stride**: a clip too short for the nominal stride now gets a *finer* rate rather than being discarded. Thirty timesteps over less real time is a speed perturbation — a standard augmentation, and strictly better than having no example of the activity.
- **Named drop reasons + stride histogram**, in the log and the manifest. The first run said "6,040 unusable" and nothing about why; finding the cause needed arithmetic on the class histogram afterwards.
- **The rate is now in the shard name** (`toyota_trimmed_20hz_0000.npz`), so re-running at a different rate can't resume against shards whose windows span a different duration and mix two rates into one training set.

## One thing I fixed before you run the untrimmed half

Integer striding would have broken window-duration parity between the two halves: 20 fps trimmed → 20 Hz → 1.50 s, but 25 fps untrimmed → 25 Hz → **1.20 s**. Same 30-frame tensor, different real time, and no field recording which — the two shard sets wouldn't be comparable.

`poses_for` now does **exact resampling** (`want = int(round(k * src / rate))`) instead of integer striding. Verified by simulation: 20 fps keeps 1200/1200 frames, 25 fps keeps 1200/1500, and a 30-frame window spans **1.45 s vs 1.44 s** — parity. It's also capped at the container rate so it can never resample *up* and invent motion. The log now reports effective rates and `window_seconds` goes into the manifest.

The carry-forward loop only copied shards matching the *current* prefix — so an untrimmed run would have copied forward `toyota_untrimmed_20hz_*` (nothing, first run), extracted its own, and published a dataset version containing **only the untrimmed half**.
